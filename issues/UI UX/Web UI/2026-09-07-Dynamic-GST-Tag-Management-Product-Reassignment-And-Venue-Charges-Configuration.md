## Issue 1: Dynamic GST Tax Tag Management and Snapshotted Order Line Architecture

| Attribute | Details |
| :--- | :--- |
| **Project Overview** | Menu Management, Order Lifecycle, and Billing Architecture — Extensible GST Tax Tag modeling with historical tax snapshot immutability. |
| **Problems Identified** | 1. The previous menu architecture relied on hardcoded or static venue-level GST percentages (5%), preventing multi-tiered tax configurations (such as 3% GST, 5% GST, or No GST) across menu items.<br>2. When a menu item's tax bracket is updated in the future, recalculating historic bills directly against current menu item definitions would corrupt historical ledger records and tax filings.<br>3. Existing order lines (`OrderItem`) did not preserve an explicit snapshot of the effective GST rate and amount at order placement time. |
| **Resolution** | 1. Implemented the `GstTaxTag` entity in `backend/prisma/schema.prisma` with `id`, `name`, `rate: Decimal(5,4)`, and `isActive`.<br>2. Linked `MenuItem` to `GstTaxTag` via `gstTaxTagId`, migrating all 24 existing menu items to `5% GST` (`rate: 0.05`).<br>3. Augmented `OrderItem` with historical snapshot fields: `gstTaxTagId`, `gstTaxTagName`, `gstRate`, and `gstAmount`.<br>4. Updated `OrderService` to calculate and freeze line item tax snapshots at order creation, ensuring subsequent GST assignment changes never mutate historical bills.<br>5. Refactored `BillingService` to compute bill subtotals, tax distributions, and final net payable from immutable snapshotted line items. |
| **Activities Completed** | 1. Extended Prisma schema and pushed database migrations using `prisma db push` and `prisma generate`.<br>2. Implemented CRUD methods (`getGstTaxTags`, `createGstTaxTag`, `updateGstTaxTag`, `getGstItemAssignments`, `bulkAssignGstTaxTag`) in `MenuService.ts`.<br>3. Integrated Redis menu cache invalidation and Socket.IO `MENU_UPDATED` real-time broadcasting.<br>4. Executed integration tests verifying order placement, tax snapshot persistence, and bill calculation across multiple tax brackets. |
| **Files / Modules Updated** | - `backend/prisma/schema.prisma`<br>- `backend/src/services/MenuService.ts`<br>- `backend/src/services/OrderService.ts`<br>- `backend/src/services/BillingService.ts`<br>- `backend/src/routes.ts`<br>- `web-frontend/src/types/index.ts`<br>- `web-frontend/src/services/api.ts` |

## Issue 4: GST Percentage Global Uniqueness, Tag Deletion with Atomic Fallback Reassignment, and Modal Layering Over Expanded Navigation

| Attribute | Details |
| :--- | :--- |
| **Project Overview** | Data Integrity, Lifecycle Deletion Safeguards, and Window Layering Architecture — Enforcing unique tax rates, safe tag removal, and portal-based modal layering. |
| **Problems Identified** | 1. GST Tax Tags permitted duplicate effective tax percentages under different names (e.g. `3 GST`, `3% GST`, `3.00% GST`), leading to ambiguous tax assignment records.<br>2. Administrators had no interface or API to delete obsolete GST tags from the Target GST dropdown, and deleting a tag risked leaving assigned menu items with orphaned tax references.<br>3. The mandatory `No GST` base tag had no deletion safeguards.<br>4. Modals rendered within normal page flow were subject to stacking-context clipping beneath the expanded Sidebar (`z-50`), and background blur effects visually merged with the sidebar.<br>5. Left panel lacked quick-filtering by existing GST assignments. |
| **Resolution** | 1. **Percentage Uniqueness**: Added `@unique` constraint to `rate` in `GstTaxTag` schema, created `normalizeGstRate(rawRate)` in `MenuService.ts` to canonicalize numeric/string inputs (`3`, `3.0`, `3%`, `0.03`), and rejected duplicates at both frontend and backend with the exact error message: `This GST percentage already exists.`.<br>2. **Target GST Delete Control**: Placed a `[ Delete ]` button beside the Target GST selector, automatically disabled when `No GST` is selected.<br>3. **Atomic Fallback Deletion**: Added `DELETE /api/gst-tags/:id` endpoint that atomically reassigns all affected menu products to `No GST` within a single `prisma.$transaction`, invalidates cache, and emits Socket.IO update.<br>4. **Deletion Dialog & Result Popup**: Implemented keyboard-navigable confirmation dialog with exact warning text, followed by an informative completion popup displaying the count of products reassigned.<br>5. **Portal Stacking & Layering**: Wrapped modal rendering in `createPortal(..., document.body)` with `z-[9999]` and child dialogs at `z-[10000]` using opaque `bg-black/85` scrim without backdrop blur.<br>6. **LEFT Panel Filter Tabs**: Added horizontal filter tabs (`All | 5% GST | 3% GST | No GST ...`) for instant, state-driven product filtering. |
| **Activities Completed** | 1. Applied Prisma schema migration and regenerated Prisma client.<br>2. Implemented `deleteGstTaxTag` backend service and route with admin authorization.<br>3. Updated `GstManagementModal.tsx` with React Portal, filter tabs, delete button, delete confirmation modal, and deletion result popup.<br>4. Automated test suite execution validating duplicate rate rejections (0.03, "0.0300", "3%", 0%), tag deletion, atomic reassignment to `No GST`, and protection against deleting `No GST`.<br>5. Verified production builds for both backend (`npx tsc --noEmit`) and frontend (`npm run build`). |

## Issue 5: Dynamic Source-Target GST Tag Decoupling, Target-Exclusion Interaction Model, and Authoritative Count Preservation

| Attribute | Details |
| :--- | :--- |
| **Project Overview** | Web Frontend Admin UI/UX & Menu Management Architecture — Dynamic decoupling of source and target GST tax tag contexts, exclusion of target tag from available source tabs, and authoritative assignment count integrity across searches and viewports. |
| **Problems Identified** | 1. **Conflation of Source Filter and Target Tag**: In the Available Products panel, clicking a GST tag previously updated `selectedTagId` (the target tag) instead of maintaining an independent source filter state (`sourceFilter`), making it impossible to treat the left panel as a dedicated source selection for reassigning items into a chosen destination tag.<br>2. **Missing General Product Pool**: The `All` tab was absent from Available Products, leaving administrators without an aggregate view of all assignable products in the venue catalog outside the selected target tag.<br>3. **Same Source and Target Ambiguity & Redundant Warnings**: Selecting the same tag on the left as on the right initially necessitated a special contextual warning banner ("You are currently viewing [Tag] as target..."), which added unnecessary UI overhead and state complexity.<br>4. **Count Derivation and Creep**: Tag badge counts were at risk of derivation from filtered or zero-match search result arrays rather than reflecting authoritative database assignment counts, and backend bulk reassignment updated items already assigned to the target tag without filtering them out.<br>5. **Search Scope Leakage**: Searching in Available Products while filtering by rate could display products already assigned to the target tag as assignable duplicates.<br>6. **Conditional Hook Execution (Rules of Hooks Violation)**: An early return guard `if (!isOpen || typeof document === 'undefined') return null;` placed prior to `useMemo` hooks caused the React runtime error `Rendered more hooks than during the previous render` whenever the modal transitioned between closed and open states. |
| **Resolution** | 1. **Decoupled State Architecture**: Separated `targetTagId` (`selectedTagId`, right panel) and `sourceFilter` (left panel, `'ALL' \| string`). Left panel clicks update exclusively `sourceFilter` and never alter `targetTagId`.<br>2. **Dynamic Target Exclusion (`visibleSourceTags`)**: Dynamically filtered out `targetTagId` from the left source tab list (`tags.filter(t => t.id !== selectedTagId)`). The currently selected target tag never appears as its own source selection, completely eliminating same-source/same-target collisions.<br>3. **Dynamic Reappearance & State Reset**: When the target tag changes, the previous target immediately reappears as a selectable source tab, the new target disappears, `searchQuery` is cleared, and if `sourceFilter === newTargetId`, it automatically resets to `'ALL'`.<br>4. **Obsolete Warning Flow Removal**: Completely removed the `isSameSourceAndTarget` warning message banner and product-list replacement block, directly rendering the search input, select-all toggle, and product checklist without intermediate warning layers.<br>5. **Authoritative Count Preservation**: Tag badge counts are calculated directly from `allItems` (`getTagAssignmentCount(tagId)`), ensuring counters remain immutable during 0-result searches or tab changes. The "All" tab badge dynamically computes `getAllAssignableCount()` (all catalog items outside `selectedTagId`).<br>6. **Backend Mutation Idempotency**: Updated `bulkAssignGstTaxTag` in `MenuService.ts` to include `where: { id: { in: itemIds }, OR: [{ gstTaxTagId: null }, { gstTaxTagId: { not: targetTag.id } }] }`, preventing duplicate reassignment and ensuring returned mutation counts accurately reflect genuine changes.<br>7. **Responsive Tab Optimization**: Configured source-tag tabs with `flex items-center gap-1.5 overflow-x-auto custom-scrollbar`, providing seamless touch scrolling on mobile (320–767px) without awkward layout wraps or gaps on tablet and desktop.<br>8. **Unconditional Hook Ordering**: Relocated `if (!isOpen || typeof document === 'undefined') return null;` strictly after all React state, ref, effect, and memoization hooks directly before JSX portal rendering, guaranteeing exact hook execution order on every render. |
| **Activities Completed** | 1. Updated `GstManagementModal.tsx` with decoupled state, dynamic `visibleSourceTags`, restored "All" tab, unconditional hook ordering, and removed obsolete warning logic.<br>2. Updated `MenuService.ts` with idempotent transaction filtering.<br>3. Automated end-to-end verification of Scenarios A through E:<br>&nbsp;&nbsp;• **Scenario A**: Target `7% GST` excludes `7% GST` from left source tabs.<br>&nbsp;&nbsp;• **Scenario B**: Switching target to `5% GST` immediately hides `5% GST` and reappears `7% GST` with its true count.<br>&nbsp;&nbsp;• **Scenario C**: Selecting `7% GST` from the left displays its products and allows movement to `5% GST`.<br>&nbsp;&nbsp;• **Scenario D**: Switching target back to `7% GST` restores `5% GST` on the left, resets search, and preserves counts with zero warning messages.<br>&nbsp;&nbsp;• **Scenario E**: Moving items between tags updates source and target counts instantly without duplicates.<br>4. Validated production builds (`npm run build` on web-frontend and `npx tsc --noEmit` on backend) with 0 errors. |
| **Files / Modules Updated** | - `web-frontend/src/components/admin/GstManagementModal.tsx`<br>- `backend/src/services/MenuService.ts` |
