## Issue 1: Application-Wide Enter Concept Keyboard Interaction Standard and Accessible Control Navigation

| Attribute | Details |
| :--- | :--- |
| **Project Overview** | Application-Wide Keyboard Interaction Standard & Accessibility Architecture — Streamlining high-frequency workstation operations (Staff Login, Check-In Wizard, KDS Stations, Waiter Settlement, Customer Portal) with context-aware Enter/Escape keybindings and roving focus. |
| **Problems Identified** | 1. High-frequency administrative and staff workstations required constant mouse movement and clicking for standard operations (submitting login forms, advancing check-in stages, selecting tables, confirming modal actions, and searching menus), causing operator fatigue.<br>2. Ad-hoc keydown listeners across modals and forms lacked context awareness, inadvertently submitting forms while typing multiline notes inside `<textarea>` elements or during ongoing async submissions (`isSubmitting`/`isLoading`).<br>3. Dialog cancel and escape actions were inconsistently handled across confirmation modals, with some modals failing to dismiss on `Escape`. |
| **Resolution** | 1. Developed three permanent, reusable hooks in `web-frontend/src/hooks/`:<br>&nbsp;&nbsp;• `useEnterKey.ts`: Context-aware `Enter` key listener with automated suppression inside `<textarea>`/`contentEditable` elements, modifier key filtering, and submission guard checks.<br>&nbsp;&nbsp;• `useRovingSelection.ts`: 1D horizontal/vertical and 2D grid roving focus navigation (`Arrow` keys + `Enter`/`Space` selection) with ARIA compliance.<br>&nbsp;&nbsp;• `useModalKeyboard.ts`: Standardized modal keyboard control mapping `Enter` to affirmative `onConfirm` and `Escape` to `onClose` without disrupting active text inputs.<br>2. Integrated standard keybindings across core workstations:<br>&nbsp;&nbsp;• `LoginPage.tsx`: Arrow keys navigate station roles; `Enter` logs in.<br>&nbsp;&nbsp;• `CheckInPage.tsx`: `Enter` validates inputs and advances stages 1 through 5; Arrow keys navigate 2D seating grid.<br>&nbsp;&nbsp;• `WaiterStationPage.tsx` & `BartenderPage.tsx`: `Enter` executes primary stage/redemption actions; `Escape` navigates back or clears scanner.<br>&nbsp;&nbsp;• `ProductCustomizer.tsx` & Customer Modals: Arrow keys select variants/modifiers; `Escape` dismisses sheets. |
| **Activities Completed** | 1. Statically verified input element exclusions (`INPUT`, `TEXTAREA`, `contentEditable`) across all hooks to prevent broken multiline comment typing.<br>2. Validated double-submission locking guards (`disabled`, `isLoading`, `isSubmitting`).<br>3. Ensured zero regressions to existing click, touch, and swipe-down mobile gestures. |
| **Files / Modules Updated** | - `web-frontend/src/hooks/useEnterKey.ts`<br>- `web-frontend/src/hooks/useRovingSelection.ts`<br>- `web-frontend/src/hooks/useModalKeyboard.ts`<br>- `web-frontend/src/pages/LoginPage.tsx`<br>- `web-frontend/src/pages/CheckInPage.tsx`<br>- `web-frontend/src/pages/CustomerLandingPage.tsx`<br>- `web-frontend/src/pages/WaiterStationPage.tsx`<br>- `web-frontend/src/pages/BartenderPage.tsx`<br>- `web-frontend/src/components/customer/ProductCustomizer.tsx`<br>- `web-frontend/src/components/modals/CheckoutConfirmationModal.tsx`<br>- `web-frontend/src/components/modals/CancelReservationModal.tsx` |

## Issue 2: Customer Real-Time Live Notification Popup Deduplication and Visibility Clock Architecture

| Attribute | Details |
| :--- | :--- |
| **Project Overview** | Customer Live Realtime Notification Architecture — Realtime event classification, 3-second visibility clock management, LIFO preemption with remaining-time preservation, and sliding deduplication protection. |
| **Problems Identified** | 1. Kitchen/Bar KDS status revert transitions (e.g. `READY → PREPARING` or `PREPARING → ACCEPTED`) previously caused duplicate popup deliveries upon dismissal, queue promotion, or re-render.<br>2. Multiple Socket.io events describing the same underlying transition (such as concurrent `table.updated` and `bill.updated` broadcasts during bill requests or ordering reopens) triggered multiple redundant customer popups.<br>3. Floating notification display timers started prematurely upon queue arrival rather than when actively visible on the user's screen, causing queued notifications to expire before presentation.<br>4. Ordinary stock quantity decrements (`10 → 9 → 8`) generated distracting visual noise on customer screens. |
| **Resolution** | 1. Re-engineered `CustomerLiveNotificationPopup` in `CustomerApp.tsx` to ensure the 3000ms display timer starts strictly when the notification becomes actively visible (`visibleStartedAt`).<br>2. Implemented LIFO preemption with remaining visible duration preservation: newly arrived high-priority notifications preempt the active popup, pausing its calculated remaining display time (`Math.max(500, prevRemaining - elapsed)`) for resumption once top popups are dismissed.<br>3. Integrated touch-based horizontal swipe-to-dismiss (`handleTouchMove` displacement > 50px) with smooth left/right slide transitions without page-scroll disruption.<br>4. Built deterministic sliding memory deduplication (`isEventDuplicate` with 8000ms cooldown) across KDS forward transitions, revert transitions (`item_status_{id}_REVERT_{prev}_TO_{curr}`), waiter request acknowledgements (`service_req_ack_{id}_{status}`), ordering lock/reopen (`bill_requested_{token}` / `ordering_reopened_{token}`), and stock availability transitions (`stock_in_{id}_{timestamp}`).<br>5. Suppressed internal operational events and ordinary stock counter changes, reserving popups solely for meaningful customer transitions. |
| **Activities Completed** | 1. Statically verified deterministic identity generation across all 17 supported realtime customer events.<br>2. Validated customer isolation rooms (`customer:token:${tokenNumber}`, `table:${tableId}`) and payload filtering.<br>3. Verified non-interference with independent blocking dialogs (`Waiter Already Notified`, `Request Bill Confirmation`, `Ordering Closed Dialog`). |
| **Files / Modules Updated** | - `web-frontend/src/context/CustomerContext.tsx`<br>- `web-frontend/src/pages/CustomerApp.tsx` |

## Issue 3: Customer Itemized Table Bill Prepaid Session Credit Notice and Double-Counting Safeguards

| Attribute | Details |
| :--- | :--- |
| **Project Overview** | Customer Itemized Table Bill & Settlement UI/UX — Informational session credit notice architecture explaining non-refundable advance check-in and paid extension balances under authoritative billing semantics. |
| **Problems Identified** | 1. Guests reviewing their itemized table bill when order consumption was fully absorbed by prepaid session amounts (advance check-in cover charge and paid session extensions) lacked clear inline communication explaining why any remaining unconsumed prepaid credit is non-refundable per venue policy.<br>2. Naive frontend calculations risked misinterpreting complimentary extensions (`additionalAmount === 0` or `isComplimentary === true`) as paid monetary contributions.<br>3. Generic always-visible "no refund" banners created confusion for customers who had placed zero orders, customers whose consumption exceeded prepaid credits, or walk-in tables without advance payments. |
| **Resolution** | 1. Isolated the authoritative calculation of itemized session extensions in `CustomerApp.tsx`, separating `initialCheckInAmount` from `paidExtensionsTotal` and ensuring complimentary extensions contribute strictly ₹0.<br>2. Formulated a strict mathematical notice predicate evaluated against authoritative billing parameters:<br>&nbsp;&nbsp;`const hasPlacedOrders = billableItems.length > 0 && grossSubtotal > 0;`<br>&nbsp;&nbsp;`const showNonRefundableCreditNotice = hasPlacedOrders && totalPrepaidSessionAmount > 0 && grandTotal === 0 && grossSubtotal < totalPrepaidSessionAmount;`<br>3. Rendered a compact, theme-compliant informational notice (`Prepaid Session Credit Notice`) directly inside the Right Column Financial Breakdown Card, positioned below the Session Extensions breakdown / Balance Before Charges and above Service Charge / Taxes / Final Amount Payable.<br>4. Styled the notice using approved Brand Purple (`bg-primary/5 border-primary/20`) and Luxury Dark gold accents (`dark:bg-[#D4AF37]/10 dark:border-[#D4AF37]/30`) with an outline `Info` icon, avoiding alarmist language or duplicated financial figures. |
| **Activities Completed** | 1. Statically verified truth table across all 9 edge cases (zero orders, exact consumption, over-consumption, complimentary extensions, paid extensions, order item cancellations).<br>2. Verified historical `Token.amountPaid` data safety with zero retroactive database mutations.<br>3. Validated responsive layout integrity and styling in both Light and Dark themes without horizontal overflow. |
| **Files / Modules Updated** | - `web-frontend/src/pages/CustomerApp.tsx` |

Synchronized `setActiveTab` routing with browser history (`window.history.pushState`), ensuring URL updates mirror active workspace tabs without full page reloads.<br>3. Removed redundant duplicate identifier in `WaiterStationPage.tsx`, consolidating tab switching logic into the primary handler that triggers lazy on-demand data fetches (`fetchRequests`, `fetchReadyItems`, `fetchActiveBills`, `fetchReservations`) and dispatches `onTabChange` to sync with the parent router.<br>4. Verified route-level permission guards so that authorized staff (Waiters, Servers, Managers, Admins) seamlessly retain their active tab on refresh. |
| **Activities Completed** | 1. Statically verified route mapping logic and tab extraction across all 5 Waiter Station workspaces.<br>2. Verified state synchronization between URL pathname, `localStorage` fallback, and component `initialTab` props.<br>3. Ensured zero duplicate declarations and verified zero-regression TypeScript compilation (`tsc --noEmit` exit code 0). |

## Issue 5: Authoritative Time Extension Real-Time Auto-Dismissal and Multi-Modal Notification Dismissal Engine

| Attribute | Details |
| :--- | :--- |
| **Project Overview** | Customer & Staff Real-Time Notification Lifecycle Architecture — Authoritative event-driven automatic dismissal of session extension popups, multi-modal input dismissal (`Enter` key & gesture swipe), and queue desynchronization protection. |
| **Problems Identified** | 1. When a dining session time extension was successfully completed (paid cash/UPI or complimentary), existing extension alert popups and queued notices remained on-screen until manual user action or timer expiration.<br>2. Live notification popups lacked standard keyboard `Enter` dismissal support, forcing customers and staff to manually click the close icon or swipe the screen.<br>3. In-flight extension confirmations failed to purge stale queued extension notifications, causing redundant extension notices to appear after the session had already been updated. |
| **Resolution** | 1. Engineered `dismissMatchingNotifications(predicate)` in `CustomerContext.tsx` to atomically evict matching notifications from both active display (`activeNotification`) and the pending LIFO stack (`notificationQueueRef`).<br>2. Connected the authoritative `session.updated` Socket.io listener to automatically purge stale `session_extended` notifications from the queue and active display as soon as the verified extension event arrives.<br>3. Extended `DataContext.tsx` with a `session.updated` listener that immediately dismisses urgent expiry alerts (`sessionAlerts`) once the authoritative new end time extends beyond the 15-minute warning window.<br>4. Added dedicated `Enter` key listeners to `CustomerLiveNotificationPopup` in `CustomerApp.tsx` that initiate the smooth 200ms slide exit (`triggerDismiss('right')`) with 20ms queue handoff while respecting active text inputs.<br>5. Preserved full support for all three dismissal paths: automatic realtime event dismissal, manual `Enter` keyboard dismissal, and fluid horizontal touch/pointer swipe dismissal. |
| **Activities Completed** | 1. Statically verified that authoritative extension completion triggers clean notification dismissal without breaking the 20ms handoff gap or LIFO queue ordering.<br>2. Verified keyboard `Enter` suppression when typing in `input`, `textarea`, or `contentEditable` fields.<br>3. Validated non-interference with unrelated notifications (KDS status updates, stock-out alerts, bill requests, table reopen notices). |
